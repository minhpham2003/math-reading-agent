# S24 — Agent suggests a branch / tangent creation and navigation

**Status:** Design closed — approved by reader  
**Updated:** 2026-11-01

**Original scenario:** The agent predicts that answering a question will significantly interrupt the main reading path and suggests a branch. The reader decides whether to accept.

**Terminology:** Parent may be the main branch or another tangent; child is a tangent branch. Tangent creation may also be requested directly by the reader.

## Approved design decisions

### S24-D01 — Copy the discussion; summarize on parent
**Classification:** Both. **Status:** Approved.  
**Decision:** Upon creation, copy the prerequisite/tangent-related messages into the tangent; replace their *visible representation* on the parent with a concise linked summary. Never delete underlying messages.  
**Agent:** Identify relevant discussion and draft the initial summary.  
**UI/data:** Copy with stable provenance; present summary on parent with history recoverable.  
**Alternatives:** Move; copy; start from a summary only. **Evidence:** Reader explicitly said messages “should be copied to the tangent branch” and “summarized on the main branch.”

### S24-D02 — Include preceding context as read-only
**Classification:** Both. **Status:** Approved — Option B, contextual inheritance.  
**Decision:** Include relevant immediately preceding parent messages as read-only context, separate from tangent-owned messages, and preserve origin/return anchor.  
**Agent:** Determine relevant context without confusing it with tangent discussion.  
**UI/data:** Clearly distinguish read-only context, owned messages, and provenance.  
**Alternative:** Only discussion messages. **Evidence:** Reader chose **B**.

### S24-D03 — Link the parent summary to the tangent
**Classification:** Interface (with data linkage). **Status:** Approved.  
**Decision:** The parent summary contains a clickable link opening its tangent; retain the link through later summary revisions.  
**UI/data:** Stable navigable parent↔child relationship.  
**Evidence:** Reader explicitly requested the link inside the summary.

### S24-D04 — Update the parent summary only on finishing
**Classification:** Both. **Status:** Approved — Option C, update on return.  
**Decision:** Initial summary remains static while tangent work continues; on explicit finishing, generate a replacement for review, never silently rewrite the parent.  
**Agent:** Generate updated summary when finishing is invoked.  
**UI:** Parent shows last approved/initial summary until save approval.  
**Alternatives:** Automatic live updates; never update; update on finishing. **Evidence:** Reader chose **C**.

### S24-D05 — Editable agent-proposed completion summary
**Classification:** Both. **Status:** Approved — Option A, explicit completion with editing.  
**Decision:** Finish tangent & return starts agent-generated editable summary; reader edits and clicks Save summary & return; then parent summary updates and navigates to origin. Merely switching branches does not finish.  
**Agent:** Produce faithful editable draft; preserve uncertainty; do not treat draft as approved.  
**UI:** Editable review and explicit save control; stable tangent link.  
**Evidence:** Reader chose **A** and specified an editable agent summary and button to make it the parent's summary. Return specifics in S25-D02.

### S24-D06 — Completed tangents can be reopened
**Classification:** Both. **Status:** Approved — Option A, reopen.  
**Decision:** Open completed tangent, continue full history; parent keeps last approved summary while editing; next finish proposes replacement for approval.  
**Agent:** Retain full history and draft revised summary after further discussion.  
**UI/state:** Reopening is editable, preserves older approved summary and history, switches status to In progress per D13.  
**Alternative:** Read-only completed tangent. **Evidence:** Reader chose **A**.

### S24-D07 — Unlimited nested tangents
**Classification:** Both. **Status:** Approved — Option A, nested tangents.  
**Decision:** A tangent can have child tangents without preset nesting depth; each child uses the same summary/return rules; finishing returns to its immediate parent.  
**Agent:** Resolve parent-child context appropriately at arbitrary depth.  
**UI/data:** Persist tree relationships and anchors; allow recursive creation and return.  
**Alternative:** Single depth. **Evidence:** Reader chose **A**.

### S24-D08 — Breadcrumbs and collapsible branch tree
**Classification:** Interface. **Status:** Approved — Option C, both navigation tools.  
**Decision:** Clickable ancestor breadcrumbs and a collapsible branch tree, highlighting current branch, with direct navigation and no permanently mandatory sidebar.  
**Alternative:** Breadcrumbs only or tree only. **Evidence:** Reader chose **C**.

### S24-D09 — Permanent tangent capability and two creation routes
**Classification:** Both. **Status:** Approved.  
**Decision:** A consistent message-level tangent icon can initiate tangent creation from anywhere; natural-language requests can perform the same operation directly without forcing the reader to click. For icon initiation, the clicked message anchors selection and agent identifies relevant surrounding context. For conversational initiation, agent finds the beginning of the ongoing tangent discussion and includes messages from there, with preceding context as appropriate.  
**Agent:** Interpret open-ended reader instructions, infer discussion origin, execute explicitly requested creation; don't present preset intellectual-intention menus.  
**UI:** Permanent unobtrusive message-level operation, not rotating suggested prompts.  
**Evidence:** Reader described permanent message icons, direct natural-language execution, then approved anchor-based icon selection and conversation-based extraction.

### S24-D10 — Create immediately, correct selection later
**Classification:** Both. **Status:** Approved — Option A, immediate create.  
**Decision:** On explicit creation request, infer selection and create/open tangent without another confirmation; let the reader adjust selection from tangent window. Proactive agent suggestions still require reader acceptance.  
**Agent:** Select relevant beginning and context; execute request without unnecessary repeated confirmation.  
**UI:** Editing available post-creation; preserve all messages.  
**Alternative:** Preview before creating. **Evidence:** Reader chose **A**, requesting edit capability in tangent.

### S24-D11 — Flexible message selection
**Classification:** Interface (with data correctness). **Status:** Approved — Option C, boundaries + individual messages.  
**Decision:** In tangent window, edit start/end boundaries and independently include/exclude individual messages; distinguish tangent-owned versus read-only context; do not delete original history.  
**Alternative:** Boundaries only or individual only. **Evidence:** Reader chose **C**.

### S24-D12 — Preview and apply selection edits
**Classification:** Interface (with transactional state handling). **Status:** Approved — Option B, preview then apply.  
**Decision:** Selection adjustments remain provisional until Apply changes; preserve existing tangent discussion and reconcile parent's visible extraction after apply.  
**Alternative:** Immediate application. **Evidence:** Reader chose **B**.

### S24-D13 — Visible tangent status
**Classification:** Interface (with state rule). **Status:** Approved — Option A, visible status.  
**Decision:** Parent summary and branch tree show In progress / Completed. Completion follows approved finish; reopening and continuing returns status to In progress.  
**Alternative:** No visible status. **Evidence:** Reader chose **A**.

## Behavioral boundary and interaction principle
Proactive *suggestion* is not proactive *execution*. Explicit reader commands such as “make this a tangent” authorize creation immediately. Intellectual goals are expressed in natural language; permanent controls support operations rather than supplying a menu of intentions.

## Additional approved decisions — S24-D14 through S24-D24

These were approved after the initial classification audit. **All original alternatives are preserved below.** A reader-authored refinement supersedes the earlier presentation of a summary as strictly replacing the parent-visible messages: parent now has a *collapsible* history container.

### S24-D14 — Hybrid tangent naming
**Status:** Approved. **Decision: Option C — Hybrid name; editable afterward.** **Classification:** Both.
- **A:** Agent generates descriptive editable name.
- **B:** Agent asks reader to name tangent before creation.
- **C (selected):** Generate title automatically unless reader supplies a title in their instruction.
- **Reader refinement:** Title remains editable later through interface or natural language.
- **Agent contract:** Extract explicit supplied title; otherwise generate concise descriptive title; handle subsequent rename instructions.
- **UI contract:** Title editable anytime, no mandatory naming step.

### S24-D15 — Icon on earlier message
**Status:** Approved. **Decision: Option A — Create immediately.** **Classification:** Both.
- **A (selected):** Create tangent immediately from clicked older message, with relevant context; correct selection later.
- **B:** Ask what to investigate before creation.
- **C:** Open draft tangent for inspection before activating.
- **Agent contract:** Identify clicked message and relevant surrounding context without forcing an objective prompt.
- **UI contract:** Open tangent immediately; title and message selection editable in tangent.

### S24-D16 — Related tangent already exists
**Status:** Approved. **Decision: Option B — Offer reuse.** **Classification:** Both.
- **A:** Always create new.
- **B (selected):** Suggest continuing existing related tangent or creating new.
- **C:** Automatically reuse existing tangent.
- **Reader-aligned qualification:** If reader explicitly says *separate/new tangent*, follow the instruction without redundant question.
- **Agent contract:** Detect close relevance but do not conflate shared topic with shared purpose or merge automatically.
- **UI contract:** Open previous tangent intact upon reuse; otherwise create new.

### S24-D17 — Transfer messages when reusing
**Status:** Approved. **Decision: Option C — Ask about transfer.** **Classification:** Both.
- **A:** Copy current messages automatically into existing tangent.
- **B:** Open existing tangent while leaving messages in parent.
- **C (selected):** Ask whether current discussion should transfer.
- **Agent contract:** Treat reuse and transfer as separate intentions; ask and honor decision.
- **UI/data contract:** If approved, extract selected messages and show linked parent summary; otherwise navigate without transfer.

### S24-D18 — Position of transferred messages
**Status:** Approved. **Decision: Option A — Append chronologically.** **Classification:** Both.
- **A (selected):** Append transferred messages after original tangent history, retaining their internal order.
- **B:** Insert messages at intellectually matching earlier location.
- **C:** Preserve transferred messages as visibly separate discussion segments.
- **Agent contract:** Do not rearrange earlier dialogue to look more logical.
- **UI/data contract:** Preserve transcript order, links and origin provenance.

### S24-D19 — Changes in tangent focus
**Status:** Approved. **Decision: Option B — Occasional contextual suggestion.** **Classification:** Agent behavior (with UI support).
- **A:** Never mention focus shifts.
- **B (selected):** Occasionally flag a substantial shift and ask whether to continue or make another tangent.
- **C:** Automatically rename/reorganize/split.
- **Agent contract:** Identify major, not minor, changes; avoid repetitive interruptions and never reorganize automatically.
- **UI contract:** Ordinary create-tangent operation if reader agrees; no special canned intellectual prompts.

### S24-D20 — Message ownership across tangents
**Status:** Approved. **Decision: Option B — Exclusive ownership.** **Classification:** Both.
- **A:** Independently copy one message as tangent-owned into multiple tangents.
- **B (selected):** Each message has exactly one owning branch; other tangents may reference it as context.
- **C:** Treat a single message as shared content appearing in multiple tangent conversations.
- **Agent contract:** Avoid duplicating ownership; use reference when useful.
- **UI/data contract:** Stable canonical message identity, one owner, read-only references and provenance. Extracted parent messages may remain visible in expandable *read-only* historical representation.

### S24-D21 — Reference appearance
**Status:** Deferred, **not approved** (belongs to Section F — References and Citations).
- **A:** Compact clickable reference.
- **B:** Inline read-only quotation.
- **C:** Expandable reference with preview and source navigation.
- **Reader correction:** Reference behavior should be consistent everywhere and not redesigned specifically for tangents.

### S24-D22 — Collapsible summary and original parent discussion
**Status:** Approved — reader-proposed revision, **no A/B/C vote**. **Classification:** Both (primarily UI).
- **Earlier D01 refinement:** Instead of showing only a summary where extracted messages were, show a collapsible container in original position.
- **Collapsed by default:** Linked summary, tangent status and open-tangent link appear in parent.
- **Expanded:** Show *only the original main/parent-branch messages selected for extraction*, in original chronological positions, with surrounding parent messages still scrollable. Do **not** display later tangent-only discussion; clicking link enters tangent for that.
- **Reader explicitly approved:** Collapsed by default; manual expanded/collapsed state remembered across navigation.
- **UI contract:** Inline expanding, no branch switch, read-only historical display; preserve status and link, independent of expansion state.
- **Agent contract:** Do not generate an answer on expand/collapse; summarize parent extraction, not unrelated later tangent dialogue.
- **Supersession note:** S24-D01's phrase “replace their visible representation” now means a **collapsed-by-default container with expandable original discussion**, not irreversible concealment. Message ownership remains as D20.

### S24-D23 — Delete versus archive tangent
**Status:** Approved. **Decision: Option C — Both deletion and archival.** **Classification:** Both.
- **A:** Delete tangent and restore extracted messages to parent; delete tangent-exclusive dialogue after confirmation.
- **B:** Archive tangent and preserve it recoverably.
- **C (selected):** Offer both separately.
- **UI/data contract — Delete:** Confirm, remove tangent and linked summary; restore extracted messages at parent positions; remove tangent-only discussion per warning. **Archive:** Hide from ordinary tree, retain complete recoverable history and collapsed Archived-linked reference at parent.
- **Agent contract:** Interpret direct delete/archive instructions as the corresponding operation, following required destructive-action confirmation; do not silently delete mathematical work.
- **Constraint:** Recoverability of archived data is essential; delete is destructive and must have an explicit warning.

### S24-D24 — Deleting a parent with child tangents
**Status:** Approved. **Decision: Option B — Preserve descendants.** **Classification:** Both.
- **A:** Delete whole subtree with confirmation.
- **B (selected):** Reattach immediate child tangents to deleted tangent's parent, preserving children's own descendant hierarchy.
- **C:** Ask whether to delete descendants or reattach them.
- **UI/data contract:** Update tree parent links and return anchors; preserve full child histories, summaries, references, status and nested structure.
- **Agent contract:** Never delete a child merely because its parent is deleted. Reparent children consistently with original provenance retained.

## Scenario closure — 2026-11-01

**Status: Design closed — reader approved.**

**Goal:** The agent can propose tangents for substantial detours; the reader can create, navigate, organize, reuse, finish, archive, and delete tangents without losing the original mathematical inquiry.

**Final user-facing flow:** Proactive tangent suggestion is not automatic creation. Reader may instead request creation naturally or use permanent message icons. Agent chooses relevant discussion and context; creates immediately when directly requested; title is editable. Parent displays a collapsed-by-default, expandable *historical* discussion with summary, status and tangent link; subsequent tangent-only discussion is visible only by opening tangent. Message ownership is exclusive. Nested tangents, breadcrumbs/tree, message-selection editor, reuse/transfer controls, summary approval, reopening, archival and safe deletion/reparenting follow D01–D24.

**UI vs agent:** Each D-entry above and D01–D13 specifies obligations separately where needed. Expression before selection: avoid proposed intellectual-intention menus. No UI or agent implementation is established by this documentation.

**Documentation / implementation / verification:** Design recorded. **Not implemented, not deployed, not tested, not verified** for S24 as a whole. Prior scripted demos of other scenarios do not constitute S24 behavior.

**Deferred:** D21 reference appearance goes to Section F; exact icon glyphs, animations and persistence technology are implementation details, not new approved conceptual decisions.
